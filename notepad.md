## Guards (`src/domain`, `src/application/idempotencies`)

- [ ] **One guard per class, behind a protocol** — today a guard is a static-method bag: `MoneyGuard` (`amount`, `currency`, `equal`), `WalletGuard` (`sign`, `currency`, `funds`), `LedgerGuard` (`currency`, `equation`, `balanced`, plus private `aligned` / `movement`), `WagerGuard` (`referenced`, `reference`, `terminal`, `move`), `IdempotencyGuard` (`same`). Static means no seam: a rule cannot be swapped, decorated, or injected, and `WagerGuard.reference` calls `WagerGuard.referenced` directly. Target shape: a `GuardProtocol` in `src/application/protocols` (input in, decision or throws out), and one class per rule implementing it, each carrying a single specific check — the same shape `PatternProtocol` + `MoneyAmountPattern` already has. Open points to settle in the specs before code: the protocol signature (throw versus boolean), the folder (`guards/` beside `patterns/`, or keep `patterns/` and drop `{concept}.guard.ts`), how the composed checks read once they are classes (`LedgerGuard.equation` currently chains `currency` → `movement`), and name collisions with the existing pattern classes (`MoneyAmountPattern` is the amount regex, not the amount guard). Touches `money/spec.md`, `wallet/spec.md`, `ledger/spec.md`, `wager/spec.md`, `idempotencies/spec.md`, `domain/AGENTS.md`, and the callers in `money.ts`, `wallet.ts`, `ledger.ts`, `wager.ts`, `wager.reference.ts`, and `idempotency.service.ts`. No guard has its own spec today: they are exercised through the entity specs, so those assertions move with the code. Not blocking the current phase.

## Retry (`src/domain/wager`, `src/infrastructure/messaging/messages`)

- [ ] **Abstract `scheduleRetry` out of the entity** — `WagerTransaction.scheduleRetry` (`src/domain/wager/wager.ts`) grew past a state transition: it checks the status inline, bumps `attempts`, and does the backoff math (`retryFactor ** (attempts - 1)`, `min(base × factor, cap)`) against four module constants (`retryFactor`, `retryBaseMs`, `retryCapMs`, `maxAttempts`) declared at the top of the file. `markPendingReference` and `exhausted` carry the rest of the same policy, so the entity knows the 1s / 2× / 60s / 12-attempt rule. Target: the entity keeps the state (`attempts`, `nextAttemptAt`) and delegates the delay to one collaborator (a `Retry` value object, or a `patterns/retry.pattern.ts` behind a protocol like the money patterns), so `wager.ts` only assigns the result. Two things to settle in the spec first: the status check belongs to the transition map / `WagerGuard`, not to an inline `if` inside `scheduleRetry`; and `OutboxMessage.scheduleRetry` (`src/infrastructure/messaging/messages/outbox-message.ts`) already computes the same `1s × 2^(attempts - 1)`, cap 60s with its own `retry` constants — the shared piece is the delay computation, not the attempt limit (12 for the wager, unbounded for the outbox). Both `src/domain/wager/spec.md` and `src/infrastructure/messaging/spec.md` spell the formula out, so one abstraction means one source and two references. Not blocking the `feat/application/pending-reference` branch that introduced it.
